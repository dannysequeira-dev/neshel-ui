---
title: Contribuir a la documentación
description: Cómo se organiza, verifica y traduce la documentación, y la lista de comprobación para componentes nuevos.
---

La documentación es código: archivos MDX en el repositorio (`apps/docs/content/docs/{en,es}`), demos en
vivo en `apps/docs/demos` y datos de API generados a partir de las declaraciones de los paquetes. Cada
cambio pasa por revisión y CI como cualquier otro código.

## Flujo de trabajo local

```bash
pnpm install --frozen-lockfile
pnpm docs:dev        # builds the packages, starts the site at http://localhost:3000
pnpm docs:api        # regenerate API data after changing a package's public types
pnpm check:docs      # coverage, translations, links, snippets, demos, configurations
pnpm docs:build      # static export to apps/docs/out
pnpm docs:preview    # serve the export locally
```

## Reglas

- **Los hechos salen del código.** Props, tipos y valores predeterminados se renderizan a partir de
  datos generados (`<ApiTable>`); nunca los copies a mano. Mejora en su lugar el JSDoc del paquete.
- **Las vistas previas son módulos reales.** Añade un archivo en `apps/docs/demos/`, regístralo en
  `demos/registry.ts` y usa `<Preview demo="…" />`. La página muestra el código de ese archivo.
- **Los fragmentos compilan.** Los bloques `tsx`/`ts` se comprueban con TypeScript. Usa `tsx fragment`
  para extractos de JSX y `no-check="motivo"` solo cuando un bloque no pueda compilar (por ejemplo
  declaraciones generadas).
- **Los enlaces** son absolutos (`/en/docs/…`, `/es/docs/…`) y se quedan dentro de su idioma.
- **Cobertura.** Las páginas de referencia indican en el frontmatter `exports` qué exports documentan;
  cada export público debe aparecer exactamente una vez por idioma.

## Traducciones

El inglés es la fuente canónica; el español lo refleja archivo por archivo.

1. Cambia la página en inglés.
2. Haz el mismo cambio en la página en español en el mismo *pull request*. `check:docs` compara entre
   ambos idiomas el conjunto de páginas, los `exports`, las vistas previas y las tablas de API.
3. Traduce las descripciones de API nuevas en `apps/docs/i18n/api.es.json` (la comprobación lista las
   que faltan).
4. Si una traducción de verdad no puede hacerse en el mismo cambio, declara la página en
   `apps/docs/translations.json` con un motivo. El sitio muestra entonces la página inglesa bajo
   `/es/` con un aviso visible de «aún no traducida»; nunca se presenta como traducida.

## Lista para componentes nuevos

- [ ] JSDoc en cada prop pública, incluido `(default \`…\`)`.
- [ ] `pnpm build:packages && pnpm docs:api`.
- [ ] Módulo(s) de demo y entrada en el registro.
- [ ] Página en inglés según el modelo de componente (propósito, importación, uso, API, variantes,
      adaptabilidad, controlado/no controlado, composición, accesibilidad, teclado, estilos,
      limitaciones, errores).
- [ ] Página en español y traducciones de las descripciones de API.
- [ ] Frontmatter `exports` que cubra cada export nuevo.
- [ ] `pnpm check:docs` y `pnpm docs:build` pasan.

## Cambios de API

Un *pull request* que cambie una API pública debe actualizar los datos de API generados (si no, el CI
falla), las páginas afectadas en ambos idiomas e incluir un *changeset*. Quienes revisan comprueban el
diff de la documentación junto con el del código.

## Responsabilidad y versiones

Los mantenedores son los responsables de la documentación. El sitio documenta la versión de `main`; en
cada versión se actualizan a la vez la página de estado, la información de versión y el registro de
cambios. El sitio se aloja en Vercel:
producción se despliega desde `main`, cada *pull request* obtiene un despliegue de vista previa y el
CI también adjunta la exportación estática como artefacto.
