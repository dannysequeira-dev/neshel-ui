## How 0.1.0 was verified after publication

- The registry serves all five packages at `0.1.0`, and each tarball's SHA-512 integrity matches the
  tarball built and validated by the release workflow byte for byte.
- `npm audit signatures` in a clean project verifies the registry signatures and provenance
  attestations of all five packages; each statement names the repository, `release.yml`, tag
  `v0.1.0` and its commit.
- A clean installation outside the repository (empty npm cache, no repository configuration) imports
  every package, resolves every exported stylesheet, renders on the server and runs the `neshel` CLI.
- The three starter ZIPs install from the registry and build.

## What is verified for every change

Automated checks run on GitHub Actions (Linux, Windows and macOS, Node 26; Linux also Node 22
and 24):

- Lint, type checks, unit and integration tests, package builds and declarations.
- Packed tarballs: manifests, exports, declarations, source maps, `publint`, `arethetypeswrong`,
  external import and type resolution; the private `core` package is never required.
- External Vite applications installed from the tarballs: Tailwind and plain CSS, configured themes,
  custom breakpoints (`extend` and `replace`), server rendering and hydration, tree-shaking.
- Chrome: computed styles, breakpoint sweeps, Capsize geometry, real keyboard and pointer interaction
  for every interactive component, nested themes across portals, reduced motion and axe-core.
- Documentation: export coverage in both languages, type-checked snippets, links and translations.
- An isolated **Next.js 16 App Router** application built from the packed packages: production
  build, server rendering, preserved `"use client"`, hydration, client state, portalled overlays in
  nested named themes, custom breakpoints and Capsize trimming.
- **Chromium, Firefox and WebKit** smoke flows of the interactive components with axe-core (Linux
  and macOS).
- Bundle-size budgets per component family, measured from the packed packages.
- The three starters, installed from deterministic ZIP archives and built outside the repository.
- A rehearsal of the versioning transition with `npm publish --dry-run`.

Full evidence: the repository's

## Known limitations

- **Screen readers: one manual pairing.** The owner evaluated NVDA with Firefox on Windows against
  this site and reported all ten protocol steps as passing. VoiceOver, Narrator and JAWS have not
  been evaluated; accessibility-tree snapshots and axe checks are automated.
- Safari itself is not automated; WebKit (Playwright) is the closest automated engine.
- Unknown well-formed breakpoint keys warn in the browser instead of throwing (the runtime has no
  configuration).
- Capsize trimming is approximate when the configured metrics do not match the rendered font.
- Sidebar children remount when moving between the desktop sidebar and the mobile drawer.
- Inline custom properties do not cross portals; pass `container`.

## Versioning policy

Neshel-UI follows semantic versioning. Before 1.0, a **minor** release (0.x → 0.y) may contain
breaking changes, always documented in the changelog; **patch** releases are fixes only. The five
public packages share one version number during 0.x.
